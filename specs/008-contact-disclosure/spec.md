# Feature Specification: アサイン確定後の連絡先情報開示

**Feature Branch**: `008-contact-disclosure`
**Created**: 2026-06-08
**Status**: Draft
**Input**: User description: "アサイン確定後の連絡先情報開示機能。電話番号をusersテーブルに追加し、assignmentがconfirmedになったときのみ運営者⇔審判間で相互開示する。運営者は確定前に電話番号登録を義務付け（APIレベルでもブロック）。審判は確定後にプロンプトで登録を促す（段階的必須）。開示はアプリ内の試合詳細・アサイン状況・担当履歴画面で行い、発信（tel:）とSMS（sms:）の2ボタンを表示。電話番号は自由入力・保存時正規化（ハイフン除去・桁数検証）。表示時はハイフン補完。"

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 運営者がアサイン確定前に双方の電話番号を確認する (Priority: P1)

運営者が審判のアサインを確定しようとしたとき、運営者自身または対象審判の電話番号が未登録であれば、確定操作がブロックされる。双方の電話番号が揃った状態でのみ確定が完了し、アサイン確定時点で連絡手段が保証される。

**Why this priority**: 連絡先開示の起点となる操作。運営者・審判どちらかの電話番号が欠けていると、当日の緊急連絡が成立しない。確定アクションをゲートにすることで、確定済みアサインには必ず双方の連絡先が揃う状態を保証できる。

**Independent Test**: 電話番号未登録の運営者または審判のアカウントで「確定」ボタンを押下し、それぞれ適切なブロックメッセージが表示されて確定できないことを確認すれば、このストーリーは単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 電話番号未登録の運営者が「確定」ボタンを押した、**When** システムが運営者の電話番号未登録を検知する、**Then** 電話番号入力フォームが表示され確定がブロックされる
2. **Given** 電話番号入力フォームが表示されている、**When** 運営者が有効な電話番号を入力して「登録して確定する」を押す、**Then** 電話番号が保存され、アサインが確定状態になる（審判が登録済みの場合）
3. **Given** 電話番号入力フォームが表示されている、**When** 運営者が「キャンセル」を押す、**Then** 確定は行われず、アサイン状態はそのまま維持される
4. **Given** 運営者は電話番号登録済みだが対象審判が未登録の状態で「確定」ボタンを押した、**When** システムが審判の電話番号未登録を検知する、**Then** 「審判の連絡先が未登録のため確定できません。審判に登録を依頼してください。」と表示され確定がブロックされる
5. **Given** 運営者・審判ともに電話番号登録済みの状態で「確定」ボタンを押した、**When** システムが双方の登録を確認する、**Then** フォームなしに直接アサインが確定される
6. **Given** フロントエンドを迂回してAPI直接呼び出しで確定を試みた、**When** 運営者または審判の電話番号が未登録、**Then** APIが400エラーを返し確定が拒否される

### User Story 2 - 確定後に運営者が審判の電話番号を確認する (Priority: P1)

運営者がアサイン状況画面で確定済みの審判の電話番号を確認し、電話またはSMSで直接連絡できる。

**Why this priority**: アサイン確定後の連絡手段の中核。当日の遅刻・欠席・会場変更などの緊急連絡に不可欠。

**Independent Test**: 確定済みアサインのある試合のアサイン状況画面で、審判の電話番号と発信・SMSの2ボタンが表示されることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** アサインが確定済みの試合のアサイン状況画面を開いた、**When** 確定済み審判の行を表示する、**Then** 審判の電話番号（ハイフン補完済み）と「📞 発信」「💬 SMS」の2ボタンが表示される
2. **Given** 確定済み審判の行が表示されている、**When** 「📞 発信」をタップする、**Then** デバイスの発信アプリが当該番号を宛先に起動する
3. **Given** 確定済み審判の行が表示されている、**When** 「💬 SMS」をタップする、**Then** デバイスのSMSアプリが当該番号を宛先に起動する
4. **Given** 確定済み審判が電話番号を未登録の場合、**When** その審判の行を表示する、**Then** 「連絡先未登録」と表示され、連絡ボタンは表示されない
5. **Given** `accepted` 状態（未確定）の審判の行を表示した、**When** アサイン状況画面を確認する、**Then** 電話番号は表示されない（確定前は非開示）

---

### User Story 3 - 確定後に審判が運営者の電話番号を確認する (Priority: P1)

審判が担当履歴画面で確定済み試合の運営者の電話番号を確認し、電話またはSMSで直接連絡できる。

**Why this priority**: 審判側からも運営者への緊急連絡（遅刻・欠席等）が必要。双方向の連絡手段が揃って初めて機能として完結する。

**Independent Test**: 確定済みアサインのある審判アカウントの担当履歴画面で、運営者の電話番号と2ボタンが表示されることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 審判の担当履歴画面で確定済み試合を表示した、**When** 該当試合の詳細を確認する、**Then** 運営者の氏名・電話番号（ハイフン補完済み）と「📞 発信」「💬 SMS」ボタンが表示される
2. **Given** 確定済み試合の運営者連絡先が表示されている、**When** 「📞 発信」をタップする、**Then** デバイスの発信アプリが当該番号を宛先に起動する
3. **Given** `notified` または `accepted` 状態の試合を担当履歴で確認した、**When** 該当試合を表示する、**Then** 運営者の電話番号は表示されない

---

### User Story 4 - 審判がLINEで参加回答後に電話番号登録を促される (Priority: P1)

審判がLINEで「参加」をタップした際、電話番号が未登録であれば、参加は受け付けた上でBotからフォローアップメッセージが届く。運営者がアサインを確定するには審判の電話番号登録が必要なため、参加回答という最も早いタイミングで登録を促す。

**Why this priority**: 確定ブロック（User Story 1）の実効性を高める導線。審判が参加意思を示した直後に促すことで、運営者が確定しようとした際に「審判が未登録でブロックされる」状況を未然に防ぐ。登録が完了して初めて確定が成立するため、P1に格上げ。

**Independent Test**: 電話番号未登録の審判がLINEで「参加」をタップし、参加受付と同時にフォローアップメッセージが届くことを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 電話番号未登録の審判がLINEで「参加」をタップした、**When** システムが参加を受け付ける、**Then** アサインが `accepted` に更新され、Botから「当日の緊急連絡のために電話番号をご登録ください」フォローアップメッセージがアプリ登録画面へのリンクつきで届く
2. **Given** フォローアップメッセージを受け取った審判が、**When** リンクからアプリにアクセスして電話番号を登録する、**Then** 登録完了後に運営者がアサインを確定できる状態になる
3. **Given** 電話番号登録済みの審判がLINEで「参加」をタップした、**When** システムが参加を受け付ける、**Then** アサインが `accepted` に更新され、フォローアップメッセージは送信されない
4. **Given** 審判がフォローアップメッセージを無視して電話番号を登録しない状態で、**When** 運営者がそのアサインを確定しようとする、**Then** 「審判の連絡先が未登録のため確定できません」とブロックされる（User Story 1 シナリオ4と連動）

---

### User Story 5 - 審判がプロフィールで電話番号を登録・更新する (Priority: P2)

審判がプロフィール画面から自分の電話番号を登録または変更できる。

**Why this priority**: 審判の電話番号登録の主要な経路。段階的必須の実現と、登録済み番号の変更に対応するために必要。

**Independent Test**: プロフィール画面に電話番号入力欄が存在し、保存後に反映されれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 審判がプロフィール編集画面を開いた、**When** 電話番号欄に番号を入力して保存する、**Then** 番号が保存され、プロフィール画面に表示される
2. **Given** 電話番号入力欄に「090-1234-5678」と入力した、**When** 保存する、**Then** 内部では「09012345678」として正規化されて保存される
3. **Given** 電話番号入力欄に「0901234」と入力した（桁数不足）、**When** 保存しようとする、**Then** エラーメッセージが表示され保存されない
4. **Given** 登録済みの電話番号を変更して保存した、**When** 保存が完了する、**Then** 新しい番号が運営者から確認できる状態に反映される

---

### Edge Cases

- 審判が電話番号を登録後に番号を変更した場合、過去の確定済みアサインに紐付く表示も最新番号に更新されるか
- 運営者の電話番号が未登録のまま（管理者がデータ操作で強制確定した場合等）、審判側の表示はどうなるか → 「連絡先未登録」表示
- 同一試合で複数の審判が確定している場合、運営者は全員の番号を一覧で確認できるか
- 電話番号に国際電話番号（+81始まり）が入力された場合の扱い → 国内番号（0始まり11桁）のみ受け付け、国際形式は対象外とする
- アサインが確定→キャンセルになった場合、電話番号の開示は取り消されるか → 取り消す（confirmed状態でのみ開示）

## Requirements *(mandatory)*

### Functional Requirements

**電話番号の登録・管理**

- **FR-001**: システムは審判・運営者ともに電話番号をプロフィールとして登録・更新できなければならない
- **FR-002**: 電話番号は自由な書式（ハイフンあり・なし）での入力を受け付け、保存時に数字のみに正規化しなければならない
- **FR-003**: システムは正規化後の電話番号が10〜11桁の数字かつ「0」始まりであることを検証しなければならない
- **FR-004**: 電話番号の表示時は、ハイフン補完した形式（例: 090-1234-5678）で表示しなければならない

**アサイン確定時の制御**

- **FR-005**: 運営者自身の電話番号が未登録の場合、システムは確定をブロックし電話番号入力を要求しなければならない
- **FR-006**: 対象審判の電話番号が未登録の場合、システムは確定をブロックし「審判の連絡先が未登録のため確定できません」と表示しなければならない
- **FR-007**: FR-005・FR-006のブロックはAPIレベルでも実施されなければならない（フロントエンドを迂回した確定試みを拒否する）
- **FR-008**: 運営者が自身の電話番号を入力・保存した後に、そのまま確定操作を完了できなければならない

**審判への電話番号登録促進**

- **FR-009**: 審判がLINEで参加回答した際に電話番号が未登録の場合、システムはフォローアップLINEメッセージを自動送信し電話番号登録を促さなければならない
- **FR-010**: フォローアップメッセージにはアプリのプロフィール登録画面へのリンクを含まなければならない

**連絡先の開示制御**

- **FR-011**: 電話番号はアサインの status が `confirmed` の場合にのみ、関係する運営者と審判の双方に開示されなければならない
- **FR-012**: `notified`・`accepted`・`declined` 状態のアサインでは電話番号は開示されてはならない
- **FR-013**: 開示は当該試合の運営者⇔各審判の1対1の関係に限定され、審判同士では互いの電話番号は開示されない

**連絡先の表示・操作**

- **FR-014**: 確定済みアサインのアサイン状況画面（運営者向け）において、審判ごとに電話番号・発信ボタン・SMSボタンを表示しなければならない
- **FR-015**: 確定済み試合の担当履歴画面（審判向け）において、運営者の電話番号・発信ボタン・SMSボタンを表示しなければならない
- **FR-016**: 発信ボタンは `tel:` プロトコル、SMSボタンは `sms:` プロトコルを使用してデバイスの標準アプリを呼び出さなければならない
- **FR-017**: 確定済みアサインの相手方の電話番号が未登録の場合、「連絡先未登録」と表示し、発信・SMSボタンは表示しない

### Key Entities

- **電話番号 (phone_number)**: ユーザーの緊急連絡先。正規化された10〜11桁の数字列として保存。確定済みアサインの相手方にのみ開示される
- **アサイン確定 (confirmed assignment)**: 運営者が試合と審判を紐付け確定した状態。この状態への遷移が電話番号開示のトリガー
- **連絡先コンポーネント**: 開示された電話番号・発信ボタン・SMSボタンを組み合わせたUI単位。アサイン状況画面・担当履歴画面で使用

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 電話番号未登録の運営者がアサイン確定操作から電話番号登録・確定完了までを2分以内に完了できる
- **SC-002**: パイロット運用開始後1ヶ月以内に、確定済みアサインを持つ運営者の電話番号登録率が100%に達する（確定時必須のため）
- **SC-003**: 確定済みアサインを持つ審判の電話番号登録率が100%に達する（確定時に審判の電話番号登録が必須のため、構造的に保証される）
- **SC-004**: 電話番号が開示されるべきでない状態（confirmed以外）では、APIレスポンスに電話番号が含まれないことが100%保証される
- **SC-005**: 試合当日における「連絡先が分からない」に起因するトラブル報告がゼロになる

---

## Assumptions

- 対象の電話番号は日本国内の携帯電話番号（080/090/070始まり11桁）または固定電話番号（0始まり10〜11桁）を想定する。国際電話番号（+81形式）はスコープ外
- 運営者（試合の作成者）も `users` テーブルに電話番号フィールドを持つ。別テーブルへの分離は行わない
- 電話番号の表示・利用はモバイルブラウザを主とするが、PCブラウザでの `tel:` / `sms:` リンクは動作しなくてもよい（スマートフォン利用が前提）
- アサインがキャンセル等により `confirmed` 以外の状態に戻った場合、電話番号の開示も取り消される
- 電話番号の表示桁数パターンは「11桁: 0XX-XXXX-XXXX」「10桁: 0X-XXXX-XXXX」の2形式を対象とする
- 電話番号の変更履歴・監査ログはMVPスコープ外とする
- 既存の LINE 通知（確定時）への電話番号の同封は本機能のスコープ外とする（アプリ内閲覧のみ）
