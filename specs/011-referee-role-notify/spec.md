# Feature Specification: 審判依頼通知のロール選択UX改善

**Feature Branch**: `011-referee-role-notify`  
**Created**: 2026-06-10  
**Status**: Draft  

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 候補者ごとにロールを指定して通知送信 (Priority: P1)

主審・副審の両方ができる審判員を候補として、主催者が「副審として依頼したい」と判断した場合でも、現在は自動的に主審として扱われてしまう。主催者が候補者を選択する際に、各候補者を主審・副審のどちらとして依頼するかを明示的に指定できるようにする。

**Why this priority**: 主審・副審どちらもできる審判員の依頼ロールが意図と異なると、審判員側が正しい役割を理解できず混乱を招く。根本となる UX 課題のため最優先。

**Independent Test**: 主審・副審両方に対応する審判候補を選択し、副審として通知送信した場合に、送信後のアサイン一覧で「副審」と表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 主審・副審どちらも対応できる審判候補が候補リストに表示されている、**When** 主催者がその候補を選択する、**Then** 試合が募集しているロールのうち候補者が対応できるロールのみを選択できるUIが表示される
2. **Given** 主審のみ対応の審判候補が候補リストに表示されている、**When** 主催者がその候補を選択する、**Then** ロール選択UIは表示されず「主審」が自動で設定される
3. **Given** 副審のみ対応の審判候補が候補リストに表示されている、**When** 主催者がその候補を選択する、**Then** ロール選択UIは表示されず「副審」が自動で設定される
4. **Given** 複数の候補者がロールを指定した状態で選択されている、**When** 主催者が「通知を送る」を実行する、**Then** 各候補者に指定したロールで通知が送られ、アサイン一覧に正しいロールが記録される
5. **Given** 主審のみを募集している試合（`referees_needed > 0`、`assistants_needed = 0`）の候補リストに主審・副審どちらも対応できる審判候補がいる、**When** 主催者がその候補を選択する、**Then** 「主審」のみが選択肢として表示され「副審」は選択できない
6. **Given** 副審のみを募集している試合（`referees_needed = 0`、`assistants_needed > 0`）の候補リストに主審・副審どちらも対応できる審判候補がいる、**When** 主催者がその候補を選択する、**Then** 「副審」のみが選択肢として表示され「主審」は選択できない

### User Story 2 - ロールに応じた通知文言の表示 (Priority: P2)

審判員がLINEで受け取る通知のヘッダーが、依頼ロールに関わらず常に「【審判募集】」と表示される。主審として依頼されているのか副審として依頼されているのかを通知を見ただけで判断できるよう、文言を改善する。

**Why this priority**: ロール選択UX（P1）が完成した後に初めて意味を持つ改善。P1 が前提となる。

**Independent Test**: 主審として通知を送った審判員のLINEに「【主審募集】」、副審として通知を送った審判員のLINEに「【副審募集】」が表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 審判員が主審として依頼通知を受信した、**When** LINEのトークルームで通知を開く、**Then** ヘッダーに「【主審募集】」と表示される
2. **Given** 審判員が副審として依頼通知を受信した、**When** LINEのトークルームで通知を開く、**Then** ヘッダーに「【副審募集】」と表示される
3. **Given** LINEの通知プレビュー（トーク一覧のサムネイル文字列）、**When** 主審・副審それぞれの通知が届いた、**Then** プレビュー文字列もそれぞれ「【主審募集】…」「【副審募集】…」と区別して表示される

---

### Edge Cases

- 候補者の `role_type` が空の場合は候補として表示しない（既存の候補取得ロジックに依存）
- 同一審判員が同一試合で既にアサイン済みの場合は重複送信を防ぐ（既存の制約に依存）
- 通知送信後にロール選択を変えて再送信する操作は本機能スコープ外（既存の重複チェックに委ねる）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ロール選択UIに表示する選択肢は、「試合が募集しているロール」と「候補者が対応できるロール」の共通部分のみに限定しなければならない
- **FR-002**: 選択可能なロールが1種類に絞られる場合（試合の募集制約または候補者の対応ロールが1つ）、ロール選択UIは表示せずそのロールを自動設定しなければならない
- **FR-003**: 通知送信時、各候補者に対して主催者が指定したロールをアサインレコードに記録しなければならない
- **FR-004**: 審判員に送信されるLINE通知のヘッダーは、依頼ロールが主審の場合は「【主審募集】」、副審の場合は「【副審募集】」と表示しなければならない
- **FR-005**: LINEのトーク一覧プレビュー（altText）も依頼ロールに応じた文言で表示しなければならない
- **FR-006**: 選択済み候補者のロールが変更された場合、送信ボタンのラベルが最新の選択状態を反映しなければならない

### Key Entities

- **Assignment（アサイン）**: 審判員と試合のひも付け。`role` フィールド（`referee` / `assistant_referee`）が依頼ロールを保持する
- **Candidate（候補者）**: `role_type` 配列で対応可能なロール一覧を持つ審判員
- **LINE通知メッセージ**: ロールに応じたヘッダーと altText を持つ Flex Message

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 主審・副審どちらも対応できる候補を選択した場合、100% のケースでロール選択UIが表示される
- **SC-002**: 単一ロール対応候補を選択した場合、追加操作なしに自動でロールが設定され、主催者の操作ステップが増加しない
- **SC-003**: 送信されたLINE通知のヘッダー文言が、指定したロールと一致している割合が 100%
- **SC-004**: アサイン一覧画面で表示されるロールラベルが、送信時に指定したロールと一致している割合が 100%
- **SC-005**: 試合が募集していないロールが通知送信時に選択・送信されるケースが 0%

## Assumptions

- 候補者の対応ロールは `role_type` 配列（`'referee'` / `'assistant_referee'`）で既に管理されており、本機能ではその変更を行わない
- 試合が募集しているロールの判定は `referees_needed > 0`（主審募集中）/ `assistants_needed > 0`（副審募集中）で行う。募集人数の上限チェック（すでに何名確定しているか）は本機能スコープ外とし、主催者の判断に委ねる
- LINE通知の送信基盤（Flex Message の構造・送信処理）は既存実装を流用する
- デスクトップ・モバイルブラウザ両対応を前提とするが、LINEアプリ内での通知表示はLINEのプラットフォーム依存部分（Flex Message 仕様）に従う
